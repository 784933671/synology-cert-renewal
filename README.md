# DS218+ / DNSPod 证书自动续期

在群晖本机为 `ttxli.cn` 现有证书自动续期并部署。使用 Let's Encrypt 和 DNSPod DNS 验证；本机部署优先使用 DSM 的 `synowebapi`，无需开放公网 80 端口。包装器使用 Python 3.8 以上标准库，无第三方 Python 依赖。

已在 NAS 完成安装、首次签发、本机导入、公网 HTTPS 校验、定时任务实测、故障邮件收件验收及重启后任务复查；部署方式、验收结果和后续复查见 [部署验收记录](DEPLOYMENT.md)。本地测试与真实签发、导入和通知验收分开记录。

当前按用户要求每天北京时间 03:18 检查一次，并在 NAS 或管理容器启动后补查一次。证书剩余不超过 48 小时时，在首次检查中续期并替换；只有每日检查时，通常在剩余 24～48 小时时执行。首次签发或材料损坏后的修复不等待该窗口；提前时间缩短后，网络或签发故障的处理余量也相应减少。

## Docker 中文管理页面

可使用 [Docker 管理层](web/README.md) 登录查看证书状态，并配置 DNSPod 凭据、提前续期天数、检查计划和成功/失败通知邮箱，查看失败归档与操作审计。管理入口为 `https://ttxli.cn:18443`，仅监听 NAS 的 `10.10.10.37`，不新增 HTTP 入口。

“运行健康”显示主机、容器和升级状态，并配置独立的任务漏跑与证书临期预警；“执行记录”显示每轮检查、换证和预检查的脱敏时间线。预警由 NAS 主机进程每分钟检查，管理容器停止时仍可运行，不另建续期任务。默认连续漏跑 2 轮、宽限 15 分钟，临期 24 小时提醒；这些预警阈值不会修改原来的提前续期天数。

“运行概览 → 立即申请并替换证书”可在确认后跳过续期时间，执行一次新证申请、替换和服务验证；一小时内禁止重复发起。普通定时检查仍按原续期窗口执行，失败恢复优先处理已有材料，不重复强制签发。管理登录支持账号密码与邮箱验证码两步验证；登录验证邮箱独立于证书通知邮箱，只能在 NAS 私有管理员终端更改，配置与恢复步骤见管理层说明。

Docker 只承载页面和管理 API；已绑定的 DSM 任务（本机原任务 7）继续执行签发、部署、验证和通知，不增加第二套续期定时器。“访问安全”页面可切换 `lan`（仅内网）与 `public`（允许任意 IPv4 来源），两种模式都保留 HTTPS、登录和请求校验，IPv6 均拒绝。当前 NAS 按用户要求使用 `public`；新安装默认 `lan`。公网访问仍需自行配置路由器端口映射。上面的域名和内网 IP 是当前 NAS 的配置，新设备在安装向导中填写自己的参数。具体步骤见 [管理层说明](web/README.md)，实际生效模式和验收结果见 [Docker 部署验收](web/DEPLOYMENT.md)。

## 一键安装与升级（推荐）

支持 DSM 7、x86_64 架构（例如 DS218+）；先在套件中心安装并启动 Docker / Container Manager，确保 Docker Compose 和 Python 3.8+ 可用，并在 DSM“控制面板 → 通知”配置、测试邮件发送。准备好 DNSPod 子账号密钥，以及 DSM 中描述唯一、DNS SAN 已包含目标域名且已绑定到待验证 HTTPS 服务的证书条目。工具沿用该条目，不自动创建域名或扩大证书覆盖范围。

在浏览器登录 [GitHub 仓库](https://github.com/784933671/synology-cert-renewal)，通过“Code → Download ZIP”下载源码，将完整压缩包上传并解压到 NAS。通过 SSH 登录 NAS 后，在解压得到的项目根目录执行；以下路径按实际解压位置调整：

```sh
cd /volume1/docker/synology-cert-renewal-main
sudo sh setup.sh
```

向导依次检查环境、安装或复用原证书执行器、确认内网与域名参数、构建 Docker 镜像、设置管理员密码和登录验证码邮箱，再启动并验证 HTTPS 与证书桥接。密钥与密码仅在 NAS 私有终端输入，不写进命令。若现有证书过期或自签、无法用于可信管理 HTTPS，向导会明确询问是否运行原任务申请或恢复有效证书；拒绝后保留进度。域名没有对应的 DNS SAN 时，应先在 DSM 准备正确的证书条目。

安装器识别精确指向本项目启动脚本的 DSM 任务；没有才新建，由 DSM 分配编号，并在服务验收通过后启用。新任务默认每小时第 17 分钟检查；已有任务保留原编号、分钟、启停及通知配置。发现重复任务、归属不符或创建结果不明确时停止，不接管或删除其他任务。内网 DNS、路由器端口映射仍需自行配置。

相同入口自动区分首次安装与已有完整看板的升级。未完成安装使用**同一份源码包**重新运行可继续；已完成的看板使用新源码包运行即进入保留配置升级。也可明确选择：

```sh
sudo sh setup.sh check
sudo sh setup.sh upgrade
sudo sh setup.sh recover
```

`check` 只读检查环境与已有部署参数，不安装、启动服务或申请证书；`upgrade` 更新完整看板，保留密码、邮箱验证、密钥、证书配置和原续期计划；`recover` 处理管理层升级中断的恢复记录，不代替证书故障恢复，也不代表新版本已上线。安装进度位于 root 私有目录 `/usr/local/share/synology-cert-setup`；不要删除它来绕过未确认的任务或恢复状态。首次安装与升级的实际 NAS 验收结果单独记录，不以本地测试代替真实收信、签发及部署验证。

仅使用脚本、无需看板时，可继续使用下面的高级分步流程。

## 仅脚本安装前准备

1. 在“控制面板 → 信息中心”确认 DSM 为 6.2.4 或 7.x。若没有 Python 3.8 以上，在套件中心安装或更新 Python3。
2. 在“控制面板 → 安全性 → 证书”找到目标证书，记录其覆盖域名和服务绑定，确保描述唯一。本机 API 模式可以保留包含空格或中文的现有描述；临时管理员模式要求英文、数字、横线或下划线组合，例如 `ttxli-cn`。
3. 首次建议在该页面导出证书，保存至安全位置。工具后续也会自动备份，最多保留最近 5 份不同证书或配置版本。
4. 确认 NAS 能访问 DNSPod API、Let's Encrypt 和 GitHub，系统时间准确。
5. 新配置在存在 `synowebapi` 时使用本机 API 模式，以 root 身份指定现有证书 ID 导入，不保存管理员密码、不创建临时账号，也不修改强制双重验证策略。没有本机命令时使用原 acme.sh 临时管理员模式；该模式遇到强制双重验证或已有 `sc-acmesh-tmp` 账号会停止。旧配置未填写 `deployment_method` 时继续采用原模式；需要切换时重新运行 `configure`。

## 腾讯云 API 权限

在腾讯云访问管理中创建专用子账号和 API 密钥，仅给 `ttxli.cn` 对应 DNSPod 域名资源授予以下操作：

- `dnspod:DescribeRecordList`
- `dnspod:CreateRecord`
- `dnspod:DescribeRecordFilterList`
- `dnspod:DeleteRecord`

`dns-policy.example.json` 提供策略模板；将资源中的主账号 UIN 和 DNSPod DomainId 替换为控制台真实值，再绑定给子账号。模板中的资源标识不是域名字符串。实际授权需要在 DNSPod/CAM 中验证。

插件仅添加、清理验证用 TXT 记录，但上述 CAM 授权是域名资源级权限，并非“只能修改 TXT”。密钥在 NAS 交互配置时输入，不要发送到聊天、提交到代码仓库或写进任务命令。

## 仅脚本首次安装

先检查是否已有 acme.sh 容器或续期任务，确认不会重复更新同一张证书后再安装。本机 NAS 的检查结果记录在部署进度中；目录存在本身不代表正在运行续期任务。

在群晖“控制面板 → 终端机和 SNMP”中开启 SSH。局域网安装不需要新增公网端口映射。通过 File Station 将整个安装包放到 NAS 的一个文件夹，然后从电脑连接 NAS：

```sh
ssh -p 22 你的用户名@NAS局域网IP
sudo -i
cd /你在NAS上放置安装包的实际路径
sh install.sh
```

若 SSH 使用其他端口，请替换 `22`。远程安装时按实际可达入口使用 `ssh -p 外部SSH端口 用户名@ttxli.cn`；NAS 内部端口与路由器外部端口可能不同，不能使用 DSM 网页端口代替。

安装脚本会检查 DSM、Python 和本机工具，下载并校验固定版本 acme.sh。已有安装目录时会停止，不覆盖配置和证书。

安装位置为 `/usr/local/share/synology-cert-renewal`。安装器不创建定时任务、不自动签发、不修改系统证书。

进入交互配置：

```sh
PYTHON=$(cat /usr/local/share/synology-cert-renewal/python-path)
"$PYTHON" -I /usr/local/share/synology-cert-renewal/certctl.py --home /usr/local/share/synology-cert-renewal configure
```

按提示选择现有证书，并填写邮箱、提前续期天数（默认 `2`，支持 `1`～`30`）、腾讯云 SecretId/SecretKey 和需要检查的 HTTPS 服务端点。只有临时管理员模式需要填写 DSM 本机 HTTP 端口，默认为 `5000`；HTTPS 常见为 `5001`，以 NAS 的实际设置为准。程序沿用选中证书已有的 DNS 域名，不自动增加泛域名或扩大覆盖范围。

新配置保存 `renew_before_days`；旧配置缺少该字段时继续原有 ACME 续期规则。固定提前天数时，包装器按证书实际到期时间控制是否调用 ACME，并同步已有域名配置中的续期日期，避免仅修改 `--days` 后仍沿用旧日期。

列表中缺失、损坏、没有 DNS SAN 或只有 IP SAN 的证书会显示“不可用”，不妨碍选择其他有效证书；选中的目标仍需通过完整校验。

本机 API 模式直接调用 `synowebapi`，临时管理员模式只连接 NAS 本机 HTTP 回环地址。导入使用指定的现有 ID，并检查描述、默认证书和服务绑定不变；导入材料使用私有临时副本，避免接口消耗 ACME 源文件。HTTPS 验证端点使用实际服务地址、端口及域名，例如本机 DSM 可使用 `127.0.0.1`、`5001`、证书实际覆盖的域名。若证书绑定在反向代理服务上，应添加相应服务端点。服务器名称用于 TLS SNI，通配符证书应填写真实子域名。

先检查，再首次运行：

```sh
"$PYTHON" -I /usr/local/share/synology-cert-renewal/certctl.py --home /usr/local/share/synology-cert-renewal check
"$PYTHON" -I /usr/local/share/synology-cert-renewal/certctl.py --home /usr/local/share/synology-cert-renewal run
"$PYTHON" -I /usr/local/share/synology-cert-renewal/certctl.py --home /usr/local/share/synology-cert-renewal status
```

`check` 用于首次安装预检，只核对旧服务证书的归属，允许旧证书过期或自签；不签发、不部署，不修改 DNS 或 DSM 业务状态，可能写入本工具日志和互斥锁。`run` 按需签发或续期，再部署并通过系统根证书验证服务实际提供的证书链、域名、有效期和叶证书指纹。缺少中间证书也会报告失败、保留待部署状态。首次部署失败时，再次执行 `run` 可重试已有证书，不需要强制重新申请。

跨轮重试和续期过程只保护目标证书的服务绑定及默认状态，其他证书的正常增删不会阻断续期。实际导入前后仍核对全部绑定；若导入期间发生变化，保留 `state/import-bindings.json` 并停止后续自动部署，核查恢复后才能继续。

签发前会持久记录当前证书及候选材料的指纹；只有来源可核实、当前证书仍符合运行基线的候选才能部署。若在 DSM 中手动替换了同一条目的证书，工具会停止并保留材料，避免把新证覆盖成历史候选。新候选在导入前还须通过系统信任库、HTTPS 服务用途和验证域名检查；导入后的真实服务验证继续保留。

确认需要重新接管外部替换的证书时，应先暂停原任务，核对当前证书、服务绑定及所有恢复/清理/通知待办。在私有 root 终端持有 `state/run.lock` 后，备份并隔离旧 ACME 目标工作目录及其对应运行基线、待部署记录，保留原件，不改 DSM 当前证书；再执行 `configure` 核对目标和 HTTPS 服务。仅在明确接受下一次会重新签发时启用任务。单独重新 `configure` 不会清除旧候选，也不能解决来源冲突；不要直接删除保护文件绕过核查。

固定提前天数时，已部署证书只要仍有效，就允许正常等待或进入续期窗口，不会因剩余不足 14 天而提前重新申请。不同指纹的新候选仍须至少剩余 14 天，并通过域名、私钥和证书链校验后才允许导入。

如果候选证书、私钥或证书链已经损坏，工具会先验证历史配置，再隔离该域名的 ACME 工作目录并重新申请，避免被未来的续期时间跳过。原有服务证书继续保留，只有新候选通过校验后才部署。提前 1～2 天的策略下，损坏材料恢复申请间隔至少 6 小时；其他策略仍为 24 小时，连续最多 3 次。取得有效候选即清除恢复计数，后续部署失败优先重试已有候选。未配置固定策略的旧配置保留原 14 天候选有效期规则。

配置、私钥、日志和备份均保存在仅 root 可访问的安装目录中。`acme.sh` 也会持久保存 API 密钥，因此备份整个目录时必须同样保护。初始化完成后可关闭 SSH；DSM 任务计划仍可运行。

## 每日及启动检查和故障通知

一键安装会自动绑定或创建任务，不要再重复创建。仅采用脚本分步安装时，在 DSM“控制面板 → 任务计划”新建“计划的任务 → 用户定义的脚本”：

- 用户：`root`。
- 计划：每天北京时间 `03:18` 执行一次，不启用每小时重复；NAS 时区设为 `Asia/Shanghai`。
- 用户定义的脚本：

```sh
/bin/sh /usr/local/share/synology-cert-renewal/run-task.sh
```

Docker 管理版在主机监督程序启动时投递一次原 DSM 任务，独立于管理页面的 HTTPS 状态；同次启动首次拉起容器不重复投递，后续单独重启容器会补查。刷新网页或 HTTPS 证书热加载不触发。暂停原任务时不投递；恢复启用后补做尚未投递的启动检查。已有续期正在运行时延后，启动后已完成的普通任务可以覆盖这次检查。投递前持久记录启动代次，结果不确定时不盲目重发，同一证书仍由原执行锁和恢复规则保护。仅脚本分步安装不包含此启动钩子。

启动脚本使用安装时探测到的 Python 绝对路径。不要依赖任务计划的交互式环境变量，也不要把 API 密钥写进任务设置。

在 DSM 中配置可用的邮件发送方式，任务设置勾选“通过电子邮件发送运行详情”和“仅当脚本异常终止时发送运行详情”。证书注册邮箱不会自动成为 DSM 的任务通知邮箱；通知邮箱需要在任务中单独填写。保存后点击“运行”，确认任务成功。另建一个临时通知测试任务，脚本填写 `exit 1`，使用相同邮件设置并手动运行，确认失败邮件送达后删除测试任务。不要修改正式任务来模拟故障。

失败通知继续使用这条 DSM 任务邮件链路。`run` 失败时输出失败阶段、中文错误摘要、安全错误码、脱敏后的详细说明、处理建议及本次归档路径，并返回非零退出码；脚本不额外发送一封失败邮件。阶段按当前操作和本轮证据区分：

| 环节 | 可报告的失败阶段 |
| --- | --- |
| 准备 | 运行前检查、部署前备份、损坏证书材料恢复 |
| 域名验证 | DNSPod 查询、创建验证 TXT、DNS 记录生效检查、证书机构验证域名 |
| 申请证书 | 证书机构账户或订单请求、签发及订单轮询、下载新证书 |
| 更新服务 | 新证书材料校验、群晖导入及绑定检查、实际 HTTPS 服务验证 |
| 收尾 | DNS 验证记录清理、发送成功邮件、记录执行结果 |

DNSPod 查询、创建和删除逐次检查接口响应，只提取白名单错误码并映射为中文摘要，例如权限不足、认证失败、网络传输失败或返回内容异常，不把云接口的原始错误消息放进邮件。证书机构阶段结合本轮 ACME 日志识别；证据不足时明确显示“证书申请流程（未定位子阶段）”或“未定位阶段”，不把通用失败猜成 DNSPod 故障。后续清理失败不会覆盖已经定位的域名验证或签发失败。

成功通知由脚本单独发送，任务计划仍保持“仅异常通知”，因此正常每日或启动检查不会发信。私有 `config.json` 可选字段 `success_notify_email` 指定成功通知收件人；当前 NAS 已设置为现有通知邮箱。字段缺省时不启用成功通知。发送使用群晖现有邮件配置和 `/bin/ssmtp`，动态读取发件地址，同时设置邮件头和信封发件人，无需再保存邮箱密码；不要把 SMTP 凭据加入本工具配置。

只有不同指纹的新证书完成替换、实际 HTTPS 验证通过且 DNS 清理完成后，才发送成功邮件，内容包含域名、完成时间、新到期时间和证书指纹。`state/success-notification.json` 保存当前基线、待通知事件和已通知指纹；首次启用只建立基线，不补发历史成功邮件，同一证书重新导入也不重复通知。发送失败保留事件，下次正常检查时只重试通知。重新 `configure` 同一证书会保留通知设置和待发送事件；切换目标证书才重新建立基线。

群晖 `ssmtp` 的标准输入使用 LF 换行，邮件程序负责转换为 SMTP 换行。脚本使用 UTF-8 正文并按这个接口格式输出，避免邮件头或编码串被显示为正文。邮件服务接受后记录已通知；若发送结果因中断未能落盘，重试使用相同 `Message-ID` 标识该事件。

工具每天及管理容器启动后检查是否进入续期窗口；未进入时不发起签发请求，并继续验证当前 HTTPS 证书。定时任务与 CLI `run` 遇到执行锁占用时最多等待 60 秒，期间仍保持互斥，取得锁后才开始证书操作；超时则跳过本轮，等待下一次计划。`check`、`configure`、`status` 和桥接调用仍采用原来的非阻塞取锁方式。等锁期间被中断不会归档为另一个正在执行任务的失败，也不会覆盖其运行结果或恢复待办。普通续期失败会随后续任务重试；任务互斥执行，部署后核验目标 HTTPS 服务实际出示的证书，失败以非零退出码报告。不要同时运行其他更新同一张证书的脚本或 DSM 任务。

每条 DNS 验证 TXT 在创建前先写入私有 `state/dns-cleanup.json`。清理按完整名称、TXT 类型和验证值精确匹配，不删除其他记录。删除请求失败、响应异常或结果尚未确认时保留清理记录；有效的新证书仍可正常部署，但任务以失败状态触发通知。下一次任务会先独立重试清理，即使尚未进入续期窗口也会执行，不会为此重复申请证书。腾讯云索引短暂延迟时，工具保留记录等待确认。

## 验收和故障处理

首次配置后确认：DNSPod 验证 TXT 记录已清理；群晖证书有效期更新；服务绑定与原来一致；浏览器访问目标域名时证书正确。Docker 管理版在 NAS 或管理容器启动后自动补查，重启后应核对执行记录；仅脚本版可手动运行一次任务。DSM 或 Python 套件升级后也要复查任务。Python 路径若发生变化，检查 `python-path` 和 `run-task.sh` 后更新到真实路径。

失败时先看邮件或任务详情里的阶段、摘要和处理建议，再查看 `status`、`state/last-result.json` 以及邮件指向的 `state/failures/failure-<UTC时间>-<唯一标识>/`。每次失败单独归档 `report.json` 和本轮已取得的操作日志、DNS 事件快照；本轮没有执行的操作不会借用上次日志作为失败证据。每次归档时清理历史，最多保留最近 30 次且不超过 30 天的完整失败记录，每份归档日志最多 256 KiB，超过限制会标明截断。归档目录为 `700`、文件为 `600`，只允许 root 访问。

邮件摘要和归档内容会脱敏 API 密钥、认证头、会话令牌、私钥及 DNS 验证值。归档失败或部分日志无法安全读取时，任务详情会明确提示日志留存异常，不会把它当作成功。`state/events.log`、`state/acme-last.log` 和 `state/dns-cleanup-last.log` 可供 NAS 本机进一步排查；后两者会被后续操作覆盖，不能代替按次归档，原始运行日志也仍需保持私有。自动备份位于 `state/backups`。

DNS 授权失败时检查 DomainId、UIN、子账号策略和 DNSPod 解析托管；DNS 验证失败时确认网络及记录传播。部署失败时核查目标 ID、唯一描述和本机 API 返回状态；临时管理员模式还需核查 DSM HTTP 端口、强制双重验证状态及临时账号。HTTPS 指纹不一致时核对服务绑定、验证端口、SNI 域名和是否经过其他代理。

恢复申请的计数与时间保存在 `state/recovery.json`，隔离的域名工作目录保存在 `state/recovery-backups`，最多保留最近 3 份，其中可能含私钥。达到恢复上限会以非零退出码通知；先检查磁盘、网络及日志，确认原因已解决后，再移除 `state/recovery.json` 并运行任务。不要通过反复清除计数连续申请证书。

若提示存在 `state/deployment-active.json`，说明任务曾异常中断。先暂停任务并核对实际服务证书、目标 ID 和绑定；临时管理员模式还需核实 `sc-acmesh-tmp` 是否为该次任务遗留账号，以及双重验证策略是否正常。确认恢复后，才移除标记并重新执行 `check`。工具不会自动删除来源不明的已有账号。

若提示前次操作后绑定发生变化，根据 `state/backups/` 恢复原绑定；若是你有意调整服务绑定，确认当前状态后重新执行 `configure` 接受新配置。不要直接删除导入绑定保护标记来忽略尚未核查的接口副作用。

DNS 清理失败时先查看本次失败归档，必要时核查 `state/dns-cleanup-last.log`、`state/acme-last.log` 和专用子账号的查询/删除权限。故障解决后再次运行任务即可重试，不要删除 `dns-cleanup.json`，否则会丢失待清理记录。清理状态包含验证值，需与原始运行日志一样保持私有。

需要恢复旧证书时，先暂停证书更新任务，在 DSM 的证书页面对同一个目标证书执行“替换现有证书”，从安全备份导入私钥、证书和中间证书，再核对原服务绑定和 HTTPS 访问。不要直接覆盖群晖系统证书目录。

分步脚本 `install.sh` 对已有目录会退出。已有完整看板使用上面的 `setup.sh upgrade` 保留配置更新；脚本用户加装看板使用 `setup.sh`，仅更新脚本则按经过验证的专用升级步骤处理。不要删掉目录后重新初始化。acme.sh 固定版本且关闭自动升级，更新后应重新验证临时管理员和证书部署行为。
